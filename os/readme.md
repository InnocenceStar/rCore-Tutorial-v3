## trap

trap本质上是一种分发机制. trap 是总入口，scause 是分拣员。 CPU 不管你是主动敲门还是被动被踢进来的，统一先 trap 到内核，然后读 scause 判断"你是谁"，再分发到对应的处理函数。

在 RISC-V 中，不管是系统调用、外部中断还是异常，CPU 都会"陷入"（trap）到同一个地方处理。

| 类型     | 触发方式                       | scause 值（示例）                                |
| -------- | ------------------------------ | ------------------------------------------------ |
| 系统调用 | 用户执行 `ecall`               | 8（Environment Call from U-mode）                |
| 外部中断 | 硬件设备发信号（时钟、键盘等） | 最高位为 1，如 5（Supervisor Timer Interrupt）   |
| 异常     | CPU 执行中出错（缺页、除零等） | 如 13（Load Page Fault）、15（Store Page Fault） |

流程:

```
ecall / 硬件中断 / 异常
        │
        ▼
  CPU 自动跳转到 stvec 指向的地址
        │
        ▼
  trap_handler()          ← 统一入口
        │
        ▼
  读 scause 寄存器
        │
        ├── scause == 8        → sys_call()    系统调用
        ├── scause 最高位 == 1  → irq_handler() 外部中断
        └── 其他               → exception()   异常处理
```

> 在 RISC-V 架构中，跳转到“跳板代码”（即 Trap Handler 入口）的过程完全由硬件自动完成，其核心机制依赖于一个关键的控制状态寄存器——stvec（Supervisor Trap Vector Base Address Register）。
> 这个寄存器存储了内核预先设置好的 trap 处理程序的起始地址。
> 当任何 trap 事件（系统调用、中断、异常）发生时，CPU 会自动将程序计数器（PC）设置为 stvec 的值，从而无条件跳转到该地址执行代码。

## 地址空间

在 Sv39 中，合法的虚拟地址只有两种：

- 高 25 位全为 0（用户空间）
- 高 25 位全为 1（内核空间）

## 分页

### satp

- [63:60] : MODE, 分页模式；
- [59:44] : ASID, 地址空间标志符，用于区分不同进程的页表缓存（TLB），通常为0；
- [43:0] : PPN, 页表基地址的物理页号；

### tips

- 页表是由寄存器satp控制开启和关闭的，开启后访问的内存地址都是虚拟地址，但是内核采用的是恒等映射；

1. 开启前（物理地址阶段）： 此时 CPU 还没开分页，代码里写的地址就是物理地址。汇编代码通常会先建立一个临时的页表，把内核所在的物理内存区域做成恒等映射。
2. 开启瞬间（sfence.vma + 写 satp）： 此时 CPU 立即切换到虚拟地址模式。
3. 开启后（虚拟地址阶段）：
   - 如果之前的映射做得好（恒等映射），那么 PC 指针指向的下一条指令的物理地址没变，虚拟地址也没变，CPU 就能顺利取指继续运行。
   - 关键点： 此时虽然代码逻辑没变，但底层的寻址方式已经彻底变了。之后所有的 HEAP_SPACE 访问，虽然看起来地址没变，但实际上都已经经过了 MMU 的翻译。

## trap & 任务切换

|          | Trap                            | 任务切换                         |
| -------- | ------------------------------- | -------------------------------- |
| 本质     | 特权级切换（用户态 → 内核态）   | 进程/线程切换（内核态 → 内核态） |
| 谁在执行 | 用户程序触发，CPU 陷入内核      | 内核调度器主动执行               |
| 地址空间 | 需要切换（用户空间 → 内核空间） | 不需要切换（全程在内核空间）     |
| 典型场景 | 系统调用、缺页异常、中断        | 时间片用完、进程阻塞、优先级调度 |

## switch

调用时机：

- 方式1：时间片用完进入中断（trap中）；
- 方式2：手动调用sys_yield;

> `__switch`是在内核栈完成的；\_\_switch 函数通常是在处理时钟中断（Time Interrupt）时被调用的。
> 但是它并不关注任务是运行在用户态还是内核态的；

### switch vs trap

> https://rcore-os.cn/rCore-Tutorial-Book-v3/chapter3/2task-switching.html

任务切换是来自两个不同应用在内核中的 Trap 控制流之间的切换。
当一个应用 Trap 到 S 模式的操作系统内核中进行进一步处理（即进入了操作系统的 Trap 控制流）的时候，其 Trap 控制流可以调用一个特殊的 switch 函数。
这个函数表面上就是一个普通的函数调用：在 switch 返回之后，将继续从调用该函数的位置继续向下执行。
但是其间却隐藏着复杂的控制流切换过程。
具体来说，调用 switch 之后直到它返回前的这段时间，原 Trap 控制流 A 会先被暂停并被切换出去， CPU 转而运行另一个应用在内核中的 Trap 控制流 B 。
然后在某个合适的时机，原 Trap 控制流 A 才会从某一条 Trap 控制流 C （很有可能不是它之前切换到的 B ）切换回来继续执行并最终返回。
不过，从实现的角度讲， switch 函数和一个普通的函数之间的核心差别仅仅是它会 换栈 。

- 与 Trap 切换不同，它不涉及特权级切换；
- 与 Trap 切换不同，它的一部分是由编译器帮忙完成的；
- 与 Trap 切换相同，它对应用是透明的。

| 特性         | Trap (`__alltraps`)                                             | Switch (`__switch`)                         |
| :----------- | :-------------------------------------------------------------- | :------------------------------------------ |
| 谁触发的？   | 硬件/异常 (时钟中断、系统调用、缺页异常)                        | 软件/调度器 (内核代码主动调用 `__switch`)   |
| 目的是什么？ | 处理事件 (响应中断，处理完后通常回到原任务)                     | 更换任务 (暂停当前任务，去运行另一个新任务) |
| 保存了什么？ | 所有通用寄存器 (x1-x31, sp, ra...) + 状态寄存器 (sstatus, sepc) | 极少部分寄存器 (仅 ra, sp, s0-s11)          |
| 存在哪里？   | 用户空间高地址的 `TrapContext` (或内核栈)                       | 任务控制块 (TCB) 里的 `TaskContext`         |
| 怎么回去？   | 通过 `__restore` 恢复所有寄存器，执行 `sret`                    | 通过 `ret` 指令直接跳回上次暂停的地方       |

为什么 switch 只存 ra 和 s0-s11 这几个？”

- 这是由 RISC-V 的调用约定 决定的：
- Caller-Saved (调用者保存): t0-t6, a0-a7。这些是临时寄存器。如果你调用了一个函数（比如 \*\*switch），你默认这些寄存器会被修改。所以不需要特意保存它们，因为当你从 \_\_switch 回来时，你也不指望它们还是原来的值。
- Callee-Saved (被调用者保存): s0-s11。这些是“永久”寄存器。如果你要用它们，必须保证用完后恢复原值。
  特殊寄存器: ra (返回地址) 和 sp (栈指针)。这两个必须保存，否则函数回不去了，栈也乱了。

### ra

ra存储的地址就是函数的返回地址，在switch.S中，就是 `__switch` 的那条指令的下一条指令地址。
switch 本质上是被当作普通函数调用的，ra 的值由调用时的 jal 或 call 指令自动设置。

具体流程如下：

- 调度器代码中有一行类似 `switch(current_task_cx_ptr, next_task_cx_ptr)` 的调用。
- 编译器会将其翻译为类似 `jal ra, switch` 的指令。
- jal 指令执行时，会自动把它自己下一条指令的地址写入 `ra`，然后跳转到 switch。
- 进入 switch 后，`sd ra, 0(a0)` 把这个地址保存到当前任务的 `taskcontext` 里。
- 所以当任务 a 被切走时，ra 里存的就是调度器中 switch 调用点之后的那条指令地址。

恢复时的完整路径

- 当任务 a 再次被调度器选中时：
- switch 从 a 的 taskcontext 中恢复 ra（即调度器中的那个地址）。
- 执行 ret，跳回调度器。
- 调度器继续执行 switch 之后的逻辑（如清理工作）。
- 最终通过 restore 恢复用户态寄存器，执行 sret 跳回用户代码。

#### ra 值的来源

\_\_switch 的 ret 跳到哪里，完全取决于 ra 的值。而 ra 的值只有两种来源：

| 来源                 | `ra` 的值                               | 对应场景         |
| -------------------- | --------------------------------------- | ---------------- |
| 创建任务时手动设置   | `__restore`,在`ch4`是`goto_trap_return` | 任务第一次运行   |
| 上次被切走时自动保存 | 调度器中调用 `__switch` 的下一条指令    | 任务被切走后恢复 |

> `goto_trap_return` 最终也会到`__restore`函数，进而回到用户栈；
> 没有第三种可能，因为一个任务要么从来没跑过（ra 是手动设的），要么跑过被切走了（ra 是自动存的）。

两种情况的区别：

- 情况一：任务没有"上次暂停的位置"，所以必须给它一个"起点"。
- 情况二：任务有"上次暂停的位置"（调度器中），直接回去接着跑就行。
